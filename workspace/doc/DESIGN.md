# 深度规划设计

> 本文回答核心问题：AI-Arena 到底是什么、海龟汤怎么让 AI 玩、怎么量化评测、分几步落地。

## 一、项目本质

**AI-Arena 是一个「离线 AI 对战评测台」**：让不同的 LLM 在社交推理游戏里当玩家相互对抗，把对局过程结构化记录成 JSON 日志，再用量化指标横向比较各模型在 **推理 / 欺骗 / 伪装 / 辩论** 四个维度上的能力差异。

我们**造的不是游戏产品，而是「能力探针 + 评测报告生成器」**。最终交付物是：可复跑的对局数据 + 可读的评测报告（图表 + 结论）。

边界钉死：**不做真人联机**（那是已挂起的 Claw 项目），所有对局是 AI vs AI 离线跑批。

## 二、最关键的设计：海龟汤让 AI 怎么玩

经典海龟汤 = 「一个知情者（GM，持汤底）+ 多个提问者，靠**是非题**逐步还原真相」。但「怎么让 AI 玩、能测出什么」有几种设计，取舍如下：

| 玩法模式 | 机制 | 能评测的维度 | 工程复杂度 | 建议阶段 |
|---|---|---|---|---|
| **A. 单 GM + 多提问者** | 脚本/强模型当 GM 守汤底，AI 轮流问是非题 | 推理 | 低 | **首发 M1** |
| B. 双盲互猜 | 两个 AI 各持一半线索，互问互答拼出全貌 | 推理 + 辩论 | 中 | M2 |
| C. 骗子变体** | 指定一名 AI 被要求说谎/隐瞒，其他人揪出骗子 | 推理 + 欺骗 + 伪装 | 高 | M5 |
| D. 辩论裁决 | 多 AI 对真相分歧，辩论说服 GM 定夺 | 辩论 | 中 | M6 |

**一个必须说清的真相**：纯经典海龟汤（GM 必须诚实答是非题）天然只突出**推理**，**欺骗/伪装几乎测不到**。项目目标里这四个维度都要覆盖，所以**最终架构必须支持「角色化变体」（模式 C）或引入狼人杀**。建议：**首发用 A 把推理评测跑通，再分步加 B/C/D，不要一上来做完美主义的多角色框架**——契合「先跑通再优化」的偏好。

## 三、技术架构与模块划分

```
AI-Arena/
├── .env                      # API key（规则2，只留模板，不写死）
├── config.toml               # 模型注册表 + 对局参数
├── engine/
│   ├── game.py               # 游戏状态机：回合/角色/胜负判定
│   ├── puzzles.py            # 题库（汤面/汤底/关键线索）
│   └── roles.py              # 角色定义（GM/提问者/骗子）
├── players/
│   ├── base.py               # Player 抽象接口（ask / answer / debate）
│   ├── llm_player.py         # litellm 统一适配
│   └── mock_player.py        # 离线假玩家（M0 先跑通用，零 key）
├── prompts/                  # 各角色 system prompt
├── run/
│   ├── single_game.py        # 单模型单局
│   └── tournament.py         # 多模型循环对战
├── eval/
│   ├── metrics.py            # 四维度指标计算
│   └── report.py             # 图表(matplotlib)+文字结论
├── logs/                     # 对局 JSON 日志
└── analysis/                 # 评测报告输出（含图，便于发小红书）
```

## 四、LLM 适配层（litellm）设计要点

- 统一入口 `completion(model=..., messages=...)`，屏蔽 OpenAI / Anthropic / DeepSeek / 通义 / Kimi 差异。
- **结构化输出**：强制模型返回 JSON（如 `{"action":"ask","content":"他喝的是水吗？"}`），便于状态机解析和日志化。
- **可观测性**：每次调用记录 token 数、延迟、成本——这本身也是评测维度（效率/性价比）。
- **降级策略**：某模型超时/不可用 → 自动 fallback 到 `mock_player`，保证对局不中断（评测 pipeline 健壮性）。

## 五、评测体系：四个维度如何量化

这是项目的「护城河」，必须想清楚怎么打分：

| 维度 | 首发可量化指标（规则+日志，不依赖另一个 LLM） | 进阶（LLM-as-Judge） |
|---|---|---|
| **推理** | 收敛步数、信息增益（每问后假设空间收缩比）、最终还原准确率 | 提问相关性/逻辑链质量评分 |
| **欺骗** | 谎言自洽度、误导成功率、被识破率 | 谎言说服力评分 |
| **伪装** | 人设一致性（偏离度）、是否「露馅」 | 角色沉浸度评分 |
| **辩论** | 说服/被说服比率、基于证据的反驳率 | 论证质量评分 |

**首发建议用「规则 + 结构化日志」评测**（M1–M4），不引入第二个 LLM 当裁判，先保证跑通和可比；M5 之后再加 LLM-as-Judge 做细粒度打分。

## 六、落地路线（里程碑）

| 里程碑 | 内容 | 交付物 | 是否依赖 API key |
|---|---|---|---|
| **M0 脚手架** | 建目录结构 + mock_player 跑通一局 | 端到端可运行 demo（假数据） | ❌ 不需要 |
| **M1 单模型单局** | 真实 LLM 当提问者，GM 用规则/脚本 | 单局 JSON 日志 | ✅ 需要 |
| **M2 题库 + 指标 v1** | 扩充题库、实现推理指标 | 单局评测分 | ❌（M1 已有 key 即可） |
| **M3 多模型对战** | tournament 循环、模型注册表 | 多模型对比数据 | ✅ |
| **M4 评测报告** | matplotlib 图表 + 文字结论 | 可读报告（图+文） | — |
| **M5 骗子变体** | 角色化，评测欺骗/伪装 | 四维度部分覆盖 | — |
| **M6 辩论环节** | 分歧辩论 + LLM-as-Judge | 四维度全覆盖 | — |

> 起步任务四条（引擎+题库 / 适配层 / 单模型单局 / 多模型+评测）≈ **M0–M4**，是现在就要做的核心。

## 七、验收标准（做到什么算「完成」）

1. 一条命令跑通一局，输出结构化 JSON 日志到 `logs/`；
2. 一条命令生成评测报告（含图表 + 文字结论）到 `analysis/`；
3. 多模型可在 `config.toml` 里配置并自动循环对战；
4. 全程零 key 也能用 `mock_player` 跑通 M0（保证 pipeline 不卡在 key 上）。

## 八、当前阻塞与建议起点

**阻塞项只有一个：项目目前是空的**（已用证据确认）。规则要求的 `.env`、`MEMORY.md` 都不存在。

**建议起点：先落地 M0**——用 `mock_player` 把整条 pipeline（引擎→对局→日志→报告）端到端跑通，完全不依赖任何 API key。这样「先跑通」立刻有抓手，之后把 key 填进 `.env` 就能无缝切换到真实模型。
